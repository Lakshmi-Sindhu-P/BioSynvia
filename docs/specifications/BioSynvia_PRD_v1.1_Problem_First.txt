Problem Statement — What BioSynvia Solves

The problem. CHO cell-culture reactors generate frequent sensor measurements, but important biological attributes
may only be measured through intermittent laboratory assays. This creates gaps in direct visibility between assay
times. Predictive models could help, yet results may be misleading if future information leaks into features or if
closely related reactor runs appear in both training and testing.

Research question. Can available inline sensor data estimate a verified, sparsely measured biological attribute
reliably on entirely unseen CHO cultivation experiments?

Proposed solution. BioSynvia will compare statistical and machine-learning soft sensors using experiment-group-
held-out evaluation, quantify error and limitations, and display qualified predictions through a read-only scientific
dashboard. Mechanistic/hybrid methods remain conditional on data suitability.

Expected outcome. A reproducible research prototype with a documented dataset, defensible model comparisons,
independent test results, uncertainty or failure analysis, and transparent interpretation—not a validated
manufacturing Digital Twin or process-control system.

1. Executive summary
1.1 Product vision

BioSynvia is a reproducible workbench for estimating sparsely measured bioprocess attributes from frequently
sampled cell-culture sensors, evaluating model reliability on new cultivation experiments, and helping scientific users
inspect predictions and their limitations. The initial application is Chinese hamster ovary (CHO-K1) cultivation at
laboratory bioreactor scale; it is not directly a CAR-T, AAV, or clinical-development system.

Its flagship output is not an attractive accuracy number. It is a complete scientific decision trail: raw-data
provenance, justified target selection, training/test discipline, baselines, model comparison, group-held-out
performance, uncertainty or failure analyses, and transparent end-user presentation. Later stages may extend the
statistical soft sensor with a simplified mechanistic or hybrid model only if the available variables support
identification and evaluation.

1.2 Detailed problem statement and opportunity

Cell-culture facilities often have frequent process-sensor measurements but relatively infrequent laboratory assays. A
scientist might want a time-resolved estimate of a biological state such as viable cell concentration, but direct
measurement may be sparse, delayed, expensive, or otherwise intermittent. A model can potentially infer an attribute
from available sensor signals. However, a model that performs well on randomly mixed records from the same
culture may fail on a new experiment, process mode, or sensor configuration. This undermines trust, interpretability,
and usefulness.

BioSynvia focuses on an under-addressed engineering requirement in many portfolio demonstrations: evaluation
must represent the scientific unit of independence. Here, 24 reactor runs arise from 12 experiments with paired
reactors. Both reactors from an experiment must stay in the same data partition. [S1, S4]

1.3 Target outcome
  •     A reproducible pipeline from source archive to documented, model-ready data.
  •     A defensible offline soft-sensor evaluation on a measured target selected after the data audit.
  •     A comparison of simple, statistical, chemometric, and selected nonlinear methods.
  •     Group-held-out evaluation, per-experiment error reports, failure diagnostics, and appropriately qualified
        uncertainty.
  •     A scientist-facing local dashboard with provenance, measured-versus-predicted trajectories, model status, and
        limitations.
  •     An optional mechanistic/hybrid modeling extension with explicit eligibility and scientific validity gates.
  •     A publishable code-and-report portfolio without implying process validation, clinical utility, regulatory
        compliance, or an operating Digital Twin.

1.4 Explicit boundaries

This product is a research prototype. It will not automate process control, release manufacturing batches, recommend
clinical treatment, claim GxP validation, connect to live bioreactors, prove cell/gene therapy expertise, or count as
professional biotech employment. Its purpose is to demonstrate scientific modeling reasoning with reproducible
evidence.

3.2 Physical and statistical meaning

Inline measurements are sampled continuously or frequently using installed instrumentation, potentially providing
real-time insight into culture conditions. Offline variables are laboratory assays collected much less frequently and
may better reflect biological attributes that sensors do not measure directly. A soft sensor is a computational estimate
of one of those hard-to-observe attributes based on signals available at inference time.

Sampling poses three distinct risks:

   1.     Temporal alignment: Sensor clocks may drift; the authors provide aligned tables. Verify how values were
          aligned, whether interpolated values are flagged, and the inference-time interpretation.
   2.     Target sparsity: An offline result exists only when assayed. Evaluation at artificially interpolated target
          points would inflate sample size and create false confidence.
   3.     Experimental dependence: The paired reactors share experiment design. Random rows, or random reactor
          splits that separate a pair, would leak closely related experimental context into evaluation.

3.4 Target selection gate (research decision T-01)

The preferred candidate is viable cell concentration/density, but this is not confirmed as a usable column. Select
the first target satisfying all of the following after Phase 1:

   •     A named, experimentally measured offline field with documented physical meaning and unit.
   •     Nontrivial coverage across multiple independent experiment IDs and both major modes where possible.
   •     Enough measured time points to support grouped evaluation without inventing labels.
   •     An unambiguous prediction use case and permissible observed-at-time covariates.
   •     No direct leakage from post-assay fields or duplicate target-derived sensors.

If viable cell density does not satisfy these criteria, examine another measured offline attribute (for example, a
documented analyte), or stop and narrow the research question. Never choose a target merely because it produces
impressive metrics.

5. Scope, releases and non-goals
5.1 MVP / V1 — required
   1.    Source manifest, license status and reproducible ingestion from legally obtained files.
   2.    Audit-ready canonical data model, target decision, unit and time contracts.
   3.    Group-aware training/development and frozen test selection.
   4.    Naive and statistical baselines plus at least one nonlinear candidate, where appropriate.
   5.    Final held-out metrics and per-experiment diagnostics with failed cases retained.
   6.    Honest uncertainty/applicability reporting, even if calibrated intervals are infeasible.
   7.    Read-only Streamlit scientific dashboard and machine-readable experiment outputs.
   8.    Readme, runnable reproduction steps, model card, tests and concise hiring-manager presentation.

5.2 V1.1 / advanced — conditional
   •     A simplified mechanistic ODE model supported by available substrates, feed/volume and biomass-related
         variables.
   •     Parameter estimation, identifiability checks, numerical verification and sensitivity analysis.
   •     Data-driven correction / hybrid model benchmarked against the same held-out experiments.
   •     Optional scenario analysis that clearly separates measured-data support from counterfactual assumptions.
   •     Broader data modality (CHO IR/fluorescence) only as a separately attributed and separately validated
         extension, not as if the datasets came from the same experiments.

5.3 Explicit non-goals
   •     Production Digital Twin, online industrial integration, closed-loop control, GMP/GxP validation or validation
         for process release.
   •     Clinical, patient or treatment recommendations; CAR-T target discovery; therapeutic claims.
   •     Claims of manufacturing process optimization or business savings not measured against real use.
   •     Deep learning for prestige; automatic integration with proprietary or J&J systems.
   •     Re-hosting uncertain-license raw datasets; use of data without documented rights.
   •     Self-promotional “90–95% fit” scores as substitutes for demonstrated competence.

7. Scientific methodology and experiment plan
7.1 Intended prediction task

Primary task (PROPOSED): Given available inline sensor measurements up to time t, estimate the chosen offline
target at time t in an experimental reactor that was not used to fit the model. The target is scored only at actual
measured offline timestamps.

Clearly distinguish:

  •      Sensor-only inference: no historical offline target values are available at runtime. This is the default primary
         soft-sensor contract.
  •      Lab-assisted inference: the most recent previously reported offline measurement can be used, only if its
         availability time is before t. Evaluate separately; never compare to sensor-only models without
         acknowledging different inputs.
  •      Forecasting: predicting future values beyond t is a different task, with additional leakage and horizon
         controls. It is out of MVP unless explicitly approved as an extension.

7.2 Unit of generalization and holdout design
  •      Group key: experiment_id, not row or reactor ID; keep the two parallel reactors together.

   •      Initial proposed final holdout: reserve two complete experiments (ideally one batch and one fed-batch if
          suitable target coverage permits). Freeze IDs before inspecting final test performance.

   •      Model development: use the remaining ten experiment groups for GroupKFold, LeaveOneGroupOut
          or another preregistered group-safe strategy; tune within development groups only.
   •      Stratification caveat: with just three fed-batch experiments, held-out performance estimates by mode are
          unstable. Report this explicitly and avoid sweeping process-mode claims.
   •      If no valid balanced two-group holdout exists: use grouped leave-one-experiment-out evaluation with
          nested tuning; designate no single inflated “unseen final test” score and disclose the limitation.
   •      Temporal consistency: if validation involves a within-run prediction setting, all features must remain past-
          only. Group independence does not by itself prevent within-row future-time leakage.

External reference: scikit-learn documents LeaveOneGroupOut/GroupKFold as methods ensuring that samples from
the same group do not cross folds. [S4]

7.3 Preprocessing and feature-policy checklist
   •      Parse source time offsets and aligned tables; document interpolation, smoothing and unit handling.
   •      Profile outliers, sensor dropouts, flatlines, spikes, duplicate time points and negative/impossible readings.
   •      Define a maximum tolerated alignment lag from observed sampling behavior; do not silently match widely
          separated measurements.
   •      Create past-only rolling medians/means, slopes, variance, missingness and elapsed-time features with a
          versioned configuration.
   •      Treat experiment-level design settings as features only if they would genuinely be known at inference and do
          not encode target-dependent outcomes.
   •      Fit imputation, scaling, PCA/PLS and feature selection inside training folds; never fit on all records before
          splitting.

   •      Keep a feature_eligibility.csv table stating source, unit, timestamp availability, intended interpretation
          and explicit leak risk.

7.5 Model selection protocol
  1.      Choose target and inference-time input contract, then freeze split groups and primary metric.
  2.      Establish naive and transparent sensor baselines before expensive modeling.
  3.      Run grouped cross-validation for each candidate under the same folds and availability constraints.
  4.      Track per-experiment MAE, RMSE, model bias, valid prediction count, missingness/failures and
          calibration/interval coverage where applicable.
  5.      Rank primarily by macro-average experiment-level MAE in original target units, not pooled point-level
          MAE, to avoid long or densely sampled runs dominating.
  6.      Prefer a simpler stable model when the nonlinear alternative’s improvement is within the uncertainty caused
          by small group counts.
  7.      Select champion and challenger without inspecting reserved final holdout; lock config; evaluate once on final
          groups.
  8.      Document unfavorable results and any post-hoc adjustment as exploratory rather than a fresh independent
          test.

Success is not an arbitrary “R² > 0.9” target. The P0 scientific success criterion is a fair comparison with baselines
and clear generalization limits. A measured improvement is desirable but must be earned on held-out groups. If no
method consistently beats the baseline, a reproducible negative result still qualifies as honest research, while the
product must not advertise accurate soft sensing.

7.6 Evaluation metrics and uncertainty
  •       Primary: macro experiment-level MAE, reported with target units; median and range across experiment
          groups.
  •       Secondary: RMSE, median absolute error, signed bias, per-mode errors, experiment-level model/baseline
          ratio, error versus cultivation time, count and percentage of predictions unavailable due to data-quality rules.
  •       Uncertainty: if appropriate, evaluate conformal or residual-based prediction intervals with group-aware
          calibration partitions; report empirical coverage and width, and acknowledge small-sample dependence.
          Avoid claiming coverage guarantees unsupported by grouping/exchangeability assumptions.
  •       Robustness: leave-one-experiment-out sensitivity, baseline ablations by sensor family
          (permittivity/turbidity/gas), sensor dropout and missingness scenarios, early-vs-late cultivation phase errors
          and batch-vs-fed-batch diagnostics.
  •       Negative evidence: a model that underperforms the baseline for an experiment must be shown, not hidden
          by an overall average.

7.7 Mechanistic/hybrid extension gate

Gate MH-01: Before fitting a mechanistic model, confirm available, correctly unitized observations for the chosen
states and inputs (e.g., substrate, biomass proxy, feed/volume for fed-batch), plus sufficient variation to estimate
parameters. If the state equations or parameter identifiability cannot be defended, run a separately labeled
synthetic simulation, not a data-calibrated biological process model.

Illustrative equations, not assumptions about this specific dataset:
Biomass proxy: dX/dt = (mu(S) - k_d) * X
Specific growth: mu(S) = mu_max * S / (K_s + S)

For substrate consumption, a growth-associated term might be related to biomass production through a yield
coefficient; fed-batch adds feed and dilution terms. These equations require review of the actual cultivation design
and measurement availability before use.

Additional science checks: plausible parameter bounds/units; solver convergence; initial-condition uncertainty;
local/global parameter sensitivity; multi-start optimization; identifiability profile; out-of-sample error relative to
statistical models; transparent distinction between descriptive fit and prospective predictive validity.

Hybrid candidate: y_hat_hybrid(t) = y_hat_ODE(t) + residual_model(sensor_history_up_to_t). Fit any
residual corrector on training groups only and evaluate the combined model on untouched experiments. An inferior
hybrid result must be reported as such.

8.2 Interaction contract

The initial app is read-only against stored artifacts. The user may choose filters, experiments, sensor families, model
versions and plots. It must not retrain a model silently, alter data, send information externally, or trigger cloud billing.
Model calculations requiring recomputation run as an explicit local CLI or controlled user action in a later release.

If a selection lacks measured target values or a model has no supported prediction, the UI must say “insufficient
evidence / unavailable” and explain why. It must not interpolate a visual curve to conceal missing ground truth.

8.3 Accessibility and performance
   •        Conventional page hierarchy and descriptive figure titles/axis labels with physical units.
   •        No reliance on color alone for measured versus estimated series.
   •        Tooltips or definitions for MAE, RMSE, uncertainty and experiment groups.
   •        On a standard local development laptop, cached dashboard pages should ordinarily load within a few
            seconds; measure actual performance before asserting an SLA.
   •        No external authentication, public account system, paid APIs or live cloud services in V1.

13. Milestone acceptance matrix and definition of done
13.1 Data-ready (M1)
  •     Source ZIP checksum verified; archive structure reconciled to 12 experiments/24 reactors or discrepancies
        recorded.
  •     All prediction-relevant fields have source/units and documented quality policy.

  •     A valid measured target is selected, or an explicit no-go decision is documented.

13.2 Model-ready (M2)
  •     Paired reactors share partitions; raw fold manifests version-controlled.
  •     Past-only features tested; preprocessing leakage tests pass.
  •     Naive baseline and candidate model protocols fixed before final evaluation.
  •     Every metric references target units, group IDs and sample counts.

13.3 Research-ready (M3)
  •     A frozen evaluation reports macro experiment-level MAE, secondary metrics, model/baseline comparison and
        failures.
  •     At least one feature-family ablation and a missing-sensor robustness check.
  •     Negative, null, unstable or mode-specific results openly described.
  •     Reproduction succeeds on a clean environment and model card is attached.

  •     A local reviewer can select an experiment and see measured/predicted trajectories, missingness and
        unsupported predictions.
  •     UI identifies input variables, data provenance and model version.

17. First implementation sprint — executable action plan
The first sprint should produce a go/no-go scientific data audit, not a flashy model. The following are ordered actions
for the developer, not claims of completed work.

  1.     Create a private repository under a neutral, renameable working path ( bioprocess-softsensor if
         preferred) with Python environment, tests and an explicit no-cloud-cost policy.
  2.     Download the archive through the publisher; log DOI, retrieved filename, byte size, checksum and the still-
         unresolved license status.
  3.     Enumerate all .xlsx and aligned CSV files; parse EXP/reactor/mode IDs from file names; verify the expected
         12×2×2 aligned file structure.
  4.     Generate machine-readable dictionaries of original and aligned columns, types, units, timestamps, invalid
         values and missingness by reactor.
  5.     Plot one representative batch and one fed-batch run with assay time markers and sensor trajectories;
         document alignment caveats.
  6.     Evaluate viable cell concentration/density and any other measured offline target against target-selection
         criteria; approve a target or stop.

  7.     Write inference_contract.md: sensor-only versus lab-assisted, cutoff time and any reporting delay
         assumptions.
  8.     Freeze proposed group split IDs after reviewing experiment metadata, without looking at final test model
         performance.
  9.     Implement the naive baseline and simple unit tests for group separation and past-only feature generation.
  10.    Review the audit pack: decide whether to proceed with model development, change target, or revise scope.

Sprint output: source manifest, data dictionary, quality report, reproducible EDA notebook, target decision, split
design, first baseline, and a short transparent scientific status report. This is the earliest useful material to show a
scientific reviewer.
